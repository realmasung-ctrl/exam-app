# Phase 9 — ทดสอบความปลอดภัยและกรณีผิดพลาด

เอกสารนี้บอก (1) สิ่งที่ระบบป้องกัน และป้องกันอย่างไร (2) วิธีทดสอบ 4 ชั้น (3) ความเสี่ยงที่ยังเหลือ

## 1. แบบจำลองภัยคุกคาม

| สิ่งที่ต้องปกป้อง | ผู้โจมตี/สถานการณ์ | การป้องกัน | ตรวจโดย |
|---|---|---|---|
| หน้าและข้อมูลของ Admin | คนทั่วไปเดา URL | middleware บังคับล็อกอิน + ทุกหน้า/action/API ตรวจสิทธิ์ซ้ำฝั่งเซิร์ฟเวอร์ + ต้องมีแถวใน `admin_profiles` | audit test, black-box ข้อ 1 |
| เฉลย | ผู้เรียนเปิด DevTools / ดู page source | หน้าสอบและ API ผู้เรียนไม่ query คอลัมน์เฉลยเลย ; หน้าผลอ่านเฉลยเฉพาะในบล็อก `canReveal()` | audit test, black-box ข้อ 4, คู่มือข้อ 3 |
| คะแนน | ผู้เรียนแก้คะแนน/เวลาในเบราว์เซอร์ | ตรวจคะแนนและเวลาในฐานข้อมูลเท่านั้น ไม่มี endpoint รับคะแนนจากผู้เรียน | edge-cases.sql, smoke.sql |
| ข้อมูลผู้เรียนคนอื่น | ผู้เรียนเปลี่ยน URL / เรียก API ตรง | ระบุตัวผู้เรียนจากโทเคนในคุกกี้ (HttpOnly) เท่านั้น ไม่มีพารามิเตอร์ระบุตัว ; DB เก็บเฉพาะ hash | audit test, black-box ข้อ 2, 6, 7 |
| ฐานข้อมูล | ผู้โจมตีนำ anon key (เปิดเผยในเบราว์เซอร์) ไปยิง Supabase ตรง | ทุกตาราง RLS เปิดโดยไม่มี policy + เพิกถอนสิทธิ์ anon/authenticated + ฟังก์ชันเรียกได้เฉพาะ service_role | security.sql, black-box ข้อ 8 |
| service_role key | รั่วไปที่เบราว์เซอร์/repo | อยู่ในไฟล์เดียว (`lib/supabase/admin.ts`, `server-only`) ; ไม่มีใน repo ; audit ห้าม client component import | audit test |
| ส่งซ้ำ / บันทึกซ้ำ | กดสองครั้ง, เน็ตสะดุด | ปิดคำตอบแบบ atomic ใน DB (`for update`) ผลสอบบันทึกครั้งเดียว ; คำขอเก่าที่มาช้าถูกทิ้งด้วยเลข seq | edge-cases.sql E8, E13 ; black-box ข้อ 5–6 |
| นาฬิกา | ผู้เรียนเลื่อนเวลาเครื่อง/ปิดแท็บ | deadline ตั้งโดย DB ; หน้าสอบนับด้วยตัวจับเวลาที่ไม่ขึ้นกับนาฬิกาเครื่อง ; หมดเวลา DB ปฏิเสธคำตอบและส่งให้เอง | edge-cases.sql E7 |
| สคริปต์แทรก (XSS) | ใส่ `<script>` ในชื่อ/คำถาม | React escape ทุกข้อความ ; ห้ามใช้ `dangerouslySetInnerHTML`/`eval` (audit บังคับ) | audit test, คู่มือข้อ 8 |
| ไฟล์ส่งออก | ชื่อผู้เรียน `=HYPERLINK(...)` | นำหน้า `'` กันสูตร Excel ; export ต้องล็อกอิน Admin | results-logic.test, black-box ข้อ 1 |
| ข้ามเว็บ (CSRF) | เว็บอื่นสั่งยิง API ในนามผู้เรียน | คุกกี้ SameSite=Lax + ตรวจ Origin ทุก endpoint ที่แก้ข้อมูล + Next.js ตรวจ Origin ของ server action | black-box ข้อ 3, 5 |
| ถูกถล่มด้วยชื่อปลอม | คนที่รู้ลิงก์สร้างผู้เข้าสอบจำนวนมาก | เพดาน 500 ผู้เข้าสอบต่อรอบ (migration 0004) | edge-cases.sql E14 |

## 2. วิธีทดสอบ 4 ชั้น (ทำตามลำดับ)

### ชั้น 1: ตรวจโค้ดอัตโนมัติ (ต้องมี Node.js 22+ ; `npm test`)
`tests/security-audit.test.ts` ตรวจ 12 กติกา เช่น ทุก action ของ Admin เรียก `requireAdmin()` ก่อน, API ผู้เรียนใช้เฉพาะโทเคนในคุกกี้, หน้าสอบไม่แตะ `is_correct`, ไม่มี key ลับใน client/repo, ทุกตารางเปิด RLS, ทุกฟังก์ชัน SECURITY DEFINER + search_path คงที่ — ถ้าการแก้โค้ดในอนาคตทำให้การป้องกันหาย การทดสอบจะล้ม
(ผมทดลองใส่ช่องโหว่ 7 แบบในสำเนาแล้ว ตรวจพบครบทุกแบบ)

### ชั้น 2: ทดสอบฐานข้อมูล (SQL Editor ไม่ต้องติดตั้งอะไร)
ทำหลังรัน migration `0004_session_cap.sql`
1. วาง `supabase/tests/security.sql` → Run → ต้องเห็นตาราง 1 แถว `✅ ALL SECURITY CHECKS PASSED` (ไม่เปลี่ยนข้อมูลใด ๆ)
2. วาง `supabase/tests/edge-cases.sql` → Run → **ต้องขึ้นข้อความ error สีแดงที่ขึ้นต้นด้วย `✅ ALL EDGE CASES PASSED`** (ตั้งใจใช้ error เพื่อให้ข้อมูลทดสอบถูกยกเลิกทั้งหมด) ข้อความอื่นที่ขึ้นต้น `FAIL:` = มีข้อที่ไม่ผ่าน ส่งข้อความมาให้ผม
   ครอบคลุม: เปิดรอบซ้ำ, ชื่อซ้ำ (ตัวพิมพ์/ช่องว่าง), โทเคนข้ามรอบ, ปิดรับแล้วคนใหม่เข้าไม่ได้แต่คนเดิมทำต่อได้, หน้าต่างเวลาเปิด-ปิดรับ, บังคับรหัสประจำตัว, หมดเวลาแล้วเวลาที่ใช้ไม่เกินเวลาที่กำหนด, ส่งซ้ำ, สอบใหม่, กระดาษเปล่า, ปัดเศษและขอบเขตเกณฑ์ผ่าน, คะแนนเท่ากัน/รายข้อ, ล้างคำตอบ, เพดาน 500 คน, ลำดับข้อ/เปลี่ยนเฉลย/ตรวจความครบถ้วน
3. `smoke.sql` เดิมยังรันได้เหมือนเดิม

### ชั้น 3: ทดสอบจากภายนอกบนเว็บจริง (black-box + โหลด 50 คน ; ต้องมี Node.js 20+)
เตรียมชุดข้อสอบ **สำหรับทดสอบ** 3–5 ข้อ ใส่คำอธิบายเฉลยข้อหนึ่งเป็นประโยคแปลก ๆ เช่น `SENTINEL-ลับ-48291` ตั้งโหมดเฉลยเป็น **“ไม่แสดงเฉลย”** แล้วเปิดรอบสอบ 15 นาที คัดลอกรหัส 16 ตัวหลัง `/e/` ในลิงก์ผู้เรียน

Windows (PowerShell) ในโฟลเดอร์โปรเจกต์:
```powershell
$env:BASE_URL="https://ชื่อเว็บของคุณ.vercel.app"
$env:CODE="รหัส16ตัว"
$env:SENTINEL="SENTINEL-ลับ-48291"
$env:EXPECT_REVEAL="hidden"
$env:SUPABASE_URL="https://xxxx.supabase.co"
$env:SUPABASE_ANON_KEY="anon key (ตัวที่เปิดเผยได้)"
node scripts/blackbox-test.mjs --load 50
```
Mac/Linux: ใช้ `export BASE_URL=...` แทน `$env:` แล้วรันคำสั่งเดียวกัน
ผลที่ต้องการ: `Summary: N passed, 0 failed` และบรรทัด `95th percentile` ต่ำกว่า 3000 ms
หมายเหตุ: ทดสอบนี้สร้างผู้เข้าสอบชื่อขึ้นต้น `bbtest` ในรอบนั้น ให้ลบรอบทดสอบทิ้งหลังจบ ถ้าบรรทัด “public sign-up is switched off” ล้ม แปลว่าการสมัครสาธารณะของ Supabase ยังเปิดอยู่ ให้ปิดแล้วลบผู้ใช้ `bbtest-…@example.com` ใน Authentication → Users

### ชั้น 4: ทดสอบด้วยมือ (ไม่ต้องติดตั้งอะไร)
ทำใน Chrome + หน้าต่างไม่ระบุตัวตน + มือถือ

1. **Admin ไม่ล็อกอิน**: เปิด `/admin`, `/admin/sets`, `/admin/results`, `/admin/settings` → ต้องเด้งไปหน้าล็อกอินทุกหน้า ; เปิด `/api/admin/sessions/<id ของรอบสอบ>/export?format=csv` → ต้องไม่ได้ไฟล์ (ขึ้น 401)
2. **บัญชีที่ไม่ใช่ Admin**: สร้างผู้ใช้ใน Supabase Authentication แต่ไม่ใส่ใน `admin_profiles` → ล็อกอินต้องถูกปฏิเสธ
3. **เฉลยต้องไม่รั่ว**: ระหว่างทำข้อสอบ กด Ctrl+U (View source) แล้วกด Ctrl+F ค้นหา `is_correct` และคำอธิบายเฉลย → ต้องไม่พบ ; DevTools → Network → กดดูคำขอ `answer`, `state` → ต้องไม่มีเฉลยในข้อมูลที่ตอบกลับ
4. **ผู้เรียนคนอื่น**: ผู้เรียน A ส่งข้อสอบแล้ว คัดลอกที่อยู่หน้าผลของ A ไปเปิดในหน้าต่างไม่ระบุตัวตน (ไม่มีคุกกี้ของ A) → ต้องเด้งไปหน้ากรอกชื่อ ไม่เห็นผลของ A
5. **คุกกี้**: DevTools → Application → Cookies → คุกกี้ `et_…` ต้องติ๊ก HttpOnly และ Secure และ SameSite=Lax ; ใน Console พิมพ์ `document.cookie` → ต้องไม่เห็นคุกกี้ `et_…`
6. **เวลาเครื่อง**: ระหว่างสอบ เลื่อนเวลาโทรศัพท์ไปข้างหน้า/ถอยหลัง 10 นาที → นาฬิกาในหน้าสอบต้องไม่กระโดด (อาจปรับเล็กน้อยเมื่อซิงก์เซิร์ฟเวอร์)
7. **ดัดแปลงคำขอ**: DevTools → Network → คลิกขวาที่คำขอ `answer` → Copy → Copy as fetch → วางใน Console แก้ `label` เป็น `จ` หรือ `question_id` เป็นข้อความมั่ว → ต้องได้ 400 ; แก้ `seq` เป็น `-1` → 400
8. **ข้อความอันตราย**: ตั้งชื่อผู้สอบเป็น `<script>alert(1)</script>` และ `' or 1=1 --` ; ใส่ข้อความเดียวกันในคำถาม/ตัวเลือก/คำอธิบายเฉลยของชุดทดสอบ → ทุกหน้า (ทำข้อสอบ ผลสอบ ตารางผล รายละเอียดรายคน) ต้องแสดงเป็นตัวอักษรตามที่พิมพ์ ไม่มีหน้าต่าง alert ขึ้น ; ส่งออก CSV/Excel แล้วเปิดต้องเป็นข้อความ
9. **สูตร Excel**: ตั้งชื่อผู้สอบเป็น `=1+1` → ส่งออก CSV/Excel → ช่องชื่อต้องเป็นข้อความ `=1+1` ไม่ใช่ 2
10. **ข้อความยาว**: ชื่อยาวเกิน 100 ตัวอักษร → ต้องถูกปฏิเสธอย่างสุภาพ
11. **รหัสผ่านอ่อน**: สร้าง Admin ใหม่ด้วยรหัสผ่านสั้นกว่า 10 ตัว → ต้องถูกปฏิเสธ
12. **สองแท็บ**: เปิดหน้าสอบเดียวกันสองแท็บ เลือกคำตอบต่างกันคนละข้อ → รีเฟรชทั้งสองแท็บ ต้องเห็นคำตอบครบทั้งสองข้อ และเวลาตรงกัน
13. **เครือข่ายสะดุด / กรณีผิดพลาดอื่น**: ใช้เช็กลิสต์ Phase 5–6 เดิม (ออฟไลน์, หมดเวลาทั้งที่เปิดหน้าไว้และปิดไปแล้ว, Admin สิ้นสุดรอบสอบกลางคัน, หลายคนพร้อมกัน)

## 3. ความเสี่ยงที่ยังเหลือ (ตั้งใจไม่ทำ หรือทำไม่ได้ในระดับเว็บ)

| ความเสี่ยง | ผลกระทบ | แนวทาง |
|---|---|---|
| ไม่มีการจำกัดจำนวนคำขอต่อ IP | คนที่รู้ลิงก์ยิงคำขอจำนวนมากได้ (ต้องมีโทเคนจึงแก้คำตอบได้ ; สร้างผู้เข้าสอบได้สูงสุด 500 ต่อรอบ) | ถ้ากังวล เปิด Vercel Firewall rate limit (แพ็กเกจที่รองรับ) หรือใช้ Cloudflare ครอบโดเมน |
| ผู้เรียนแชร์ข้อสอบ/แคปหน้าจอ/ถามกันเอง | ป้องกันไม่ได้ด้วยเว็บ | ลดผลด้วยเวลาสั้น, แบ่งห้อง, ภายหลังเพิ่มสุ่มลำดับข้อ/ตัวเลือก (นอกขอบเขตเฟสแรก) |
| ผู้เรียนเปลี่ยนเครื่อง/ล้างคุกกี้ | เข้าสอบเดิมไม่ได้ | Admin กด “อนุญาตสอบใหม่” (ได้เวลาเต็มอีกครั้ง) |
| บัญชี Admin ถูกเดารหัส/ขโมย | เห็นข้อมูลทั้งหมด | รหัสผ่าน ≥ 10 ตัว ; Supabase จำกัดความถี่ล็อกอินให้ ; แนะนำเปิด MFA ให้บัญชี Supabase/GitHub/Vercel ของผู้ดูแล |
| ไม่มี Content-Security-Policy | ชั้นป้องกัน XSS ชั้นที่สอง | ชั้นแรก (React escape + audit) ยังป้องกันอยู่ ; ใส่ CSP แบบ nonce ได้ภายหลัง |
| แพ็กเกจฟรีของ Supabase **ไม่มี backup อัตโนมัติ** และหยุดโปรเจกต์ถ้าไม่ใช้งานนาน | ข้อมูลสูญหาย/ระบบหยุด | Phase 10: ปุ่ม/สคริปต์สำรองข้อมูล + คู่มือกู้คืน ; มี cron keep-alive รายวันแล้ว |
| นาฬิกาเซิร์ฟเวอร์เว็บกับฐานข้อมูลต่างกันเล็กน้อย | เสี่ยงส่งก่อนเวลาเป็นมิลลิวินาที | ใช้เวลาของฐานข้อมูลตัดสินทั้งหมด ; ฝั่งเว็บหน่วง 2 วินาทีก่อนส่งแทน และหน้าสอบหน่วง 1.2 วินาที |
